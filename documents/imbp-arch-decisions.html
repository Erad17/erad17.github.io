Architecture Decision Record

Integrative Mind-Body Psychiatry
Rebuild Architecture

Three decisions where this build deliberately diverges from Dolphin Academic Prep — the circadian phase system, the serial essay content model, and clinical configuration as theme options. Same SPA→CMS pipeline, different answers, because the prototype asked different questions.

Project: Integrative Mind-Body Psychiatry Prototype: integrative-psych.html Stack: Timber v2 + Carbon Fields

Context

A clinical journal, not a tutoring site.

The prototype is an editorial clinical journal — paper canvas, pine & sage, glacier blue, gold-leaf hairlines — for a solo telehealth psychiatry practice serving Utah. It arrived as a single monolithic SPA: nine hash-routed views, 829 DOM nodes, 485 CSS rules, 82 JavaScript functions, and a circadian design system that shifts the ambient palette with the visitor's local time.

Like Dolphin Academic Prep, this theme was produced by the SPA→CMS pipeline — the deterministic Phase 1 parser, the AI section-map inference, and the Phase 2/3 generators emitted the same artifact set: section-map.json, css-route-map.json, CPT registrations (includes/cpts.php), the Twig component library under views/, scoped per-component CSS and JS, global.css + shared.js, and the Phase 3 seeders. Pipeline methodology is documented in the SPA→CMS Pipeline appendix; this record covers only the decisions specific to this project.

Why a mini ADR. Dolphin's rebuild needed eight decisions to escape a fifteen-year-old theme and ten plugins. This build started from a clean, well-structured prototype — so the interesting decisions are not "what to replace" but how to preserve what the prototype already got right while making it editable. Three decisions carry that weight.

Decision 1

Circadian Phase System Over Static Theme

01

CSS custom properties on :root, driven by a client-side phaseForHour() — no server dependency

Context. The prototype carries five circadian phases — dawn, morning, midday, dusk, night — that shift three ambient tokens (--ambient-a, --ambient-b, --ambient-c) on :root based on the visitor's local hour. The hero landscape art, the phase label, and the footer's "tonight" copy all follow the phase. Unlike Dolphin's holiday capsule system — date-based, discrete, tied to specific observances — this is a continuous ambient system: every visitor, every day, sees the light of their own hour.

Decision. Implement exactly as the prototype does: a phaseForHour() function in shared.js resolves the hour into a phase key, applyPhase() sets the data-phase attribute on <html>, and the phase tokens re-resolve through the CSS cascade — no style recalculation, no class swapping. Dark mode stacks on top of the phase tokens rather than replacing them ([data-theme="dark"][data-phase="dusk"] overrides --ambient-a alone), so night reading keeps a trace of the hour. A five-minute interval re-checks the phase; applyPhase() emits phase:change on the event bus so components can react without polling.

// assets/js/shared.js — Phase 2d (prototype §3, ported verbatim) function phaseForHour(h) { if (h >= 5 && h < 9) return { key: 'dawn', label: 'dawn', greeting: 'Good morning' }; if (h >= 9 && h < 12) return { key: 'morning', label: 'morning', greeting: 'Good morning' }; if (h >= 12 && h < 17) return { key: 'midday', label: 'midday', greeting: 'Good afternoon' }; if (h >= 17 && h < 20) return { key: 'dusk', label: 'dusk', greeting: 'Good evening' }; return { key: 'night', label: 'night', greeting: "It's late" }; } function applyPhase(force, root) { const p = phaseForHour(new Date().getHours()); if (!force && currentPhase === p.key) return; currentPhase = p.key; document.documentElement.setAttribute('data-phase', p.key); // … phase label, hero art variant, tonight copy, [data-art] landscapes … emit('phase:change', { phase: p.key, label: p.label, greeting: p.greeting }); } setInterval(() => applyPhase(false), 300000); // circadian re-check every 5 min

Alternative rejected: server-side theme selection via PHP time check. Rendering the phase server-side would let PHP stamp data-phase at request time — but the prototype already had the client-side system working, and porting it would add PHP complexity for zero design gain. Worse, it would interact badly with page caching: a dusk-stamped page cached at 7 p.m. and served at 9 p.m. shows the wrong light. The client-side clock is also the visitor's clock — a Utah patient reading at 10 p.m. gets night regardless of where the server lives.

The Dolphin comparison. This is the same technique as Dolphin's holiday capsule system (Decision 7 in its ADR) with a different scheduling model. Both write CSS custom properties on :root, both fail to the default brand when anything breaks, both have zero server dependencies. The capsule system switches discrete palettes on calendar dates — fourteen-plus observances a year; the circadian system interpolates across five hourly bands, every day, forever. Same tool, different time constant.

Approach Scheduling Assessment
Circadian phases (chosen) Continuous — five hourly bands, client clock Preserves the prototype's ambient design verbatim; cache-safe (phase resolves after paint); dark mode stacks on the phase tokens; zero server dependency.
Holiday capsules (Dolphin's model) Discrete — calendar dates, specific observances Wrong fit for a daily-reading clinical journal — the light should follow the hour, not the calendar. Would discard the prototype's core ambient concept.
Server-side PHP phase Continuous — server clock at render time Adds PHP complexity to a solved client-side problem; page-cache fragmentation serves stale phases; the server's timezone is the wrong reference frame for telehealth patients.
Static theme None Loses the signature design behavior — the site would no longer "know what time it is for you," which the copy leans on ("It is already evening where you are…").

Decision 2

Serial Essay CPT with Native post_content

02

WordPress post_content for the essay body, Carbon Fields for the folio metadata

Context. The practice's signature content is thirteen serial essays across two series — nine of thirty perimenopause days, four of twelve relationships days — each with body paragraphs, a dek, a pull quote, a margin note, and topic-domain tags. Unlike Dolphin's portal form entries (structured fields, encrypted at rest), essays are editorial content: long-form, sequential, published almost daily, and meant to be read in order — "day 9 assumes you read day 3."

Decision. Use WordPress's native post_content for the essay body — the prototype's body[] array maps one element per paragraph, joined on blank lines, and the essay template splits it back with wpautop() applied per part. Everything folio-specific is Carbon Fields metadata: series (a select storing the series slug), day, read, dek, pull (injected after the third paragraph), margin{label,text}, and domains (a set feeding the archive search haystack). Timber resolves the single view by CPT slug — single-imbp_essay renders views/pages/essay.twig — and the post slug maps directly onto the SPA hash route: #/essays/the-3-am-wake-up becomes /essays/the-3-am-wake-up/.

// includes/cpts.php — Phase 2a (abridged) register_post_type( 'imbp_essay', [ // body[] → post_content: one prototype array element per paragraph. 'supports' => [ 'title', 'editor', 'revisions' ], 'has_archive' => false, // the #/essays page renders the grids 'rewrite' => [ 'slug' => 'essays', 'with_front' => false ], ] ); Container::make( 'post_meta', 'Essay Details' ) ->where( 'post_type', '=', 'imbp_essay' ) ->add_fields( [ Field::make( 'select', 'series', 'Series' ) // stores the series slug — the join key ->add_options( get_series_options() ), Field::make( 'text', 'day', 'Day number' ), Field::make( 'textarea', 'dek', 'Dek' ), Field::make( 'textarea', 'pull', 'Pull quote' ), Field::make( 'complex', 'margin', 'Margin note' ), Field::make( 'set', 'domains', 'Topic domains' ), ] );

Alternative rejected: a Carbon Fields complex repeater for body paragraphs. A repeater would keep every folio field in one metabox — but post_content gives editors the WordPress editor they already know, native revisions on every save (an audit trail for clinical writing), and integration with any future SEO or feed plugin that expects real content rather than meta. The body is the essay; it should not be metadata.

The parse-map miss. The Phase 1 section map did not detect the SERIES array at all — it is a keyed lookup object rather than a rendered list, so neither the repeater detector nor the data-array scan caught it. The Phase 2a agent discovered it reading the JS source while mapping field keys, and registered imbp_series as a CPT because the essay architecture cannot function without it: essays join on the series slug, and the index cards, archive grouping, and folio progress tracker all read series totals. The miss and its recovery are recorded in the cpts.php header so the discrepancy is traceable, not silent.

Approach Assessment
Native post_content + Carbon metadata (chosen) Editors get the editor they know; revisions come free; the body is first-class content for search, feeds, and future SEO tooling; the pull quote and margin note stay structured and position-stable in the template.
Carbon Fields repeater for body paragraphs Uniform metabox, but the essay body becomes meta — no native revisions, no editor familiarity, no feed/SEO surface, and paragraph-level wpautop handling must be reimplemented.
Custom tables Maximum control, maximum cost — hand-rolled admin UI, no REST, no revision history, and a migration burden the practice gains nothing from.

Decision 3

Reflection Map as Theme Options, Not CPT

03

Clinical configuration lives in a Carbon Fields theme-options container — scored entirely client-side

Context. The Root-Cause Reflection Map is the practice's signature tool: eight questions, thirty-three answer options, each option carrying per-system weights (sleep, mood, hormones, gut, stress), a ring assignment (mind / body / gut), and — on the final history question — a care-lane routing key. It renders the visitor's answers as a living mind-body-gut pattern and a lane recommendation. This is clinical configuration: it changes infrequently, and when it changes, it changes with intent.

Decision. Store it as a Carbon Fields Theme Options container ("Root-Cause Reflection Map"), not as a CPT. The prototype's nested weight map — o.w{sleep,mood,hormones,gut,stress} — is flattened to w_* number sub-fields (0–3, an absent key equals 0) so the editor presents one row per weight rather than a nested object. The container is localized to window.IntegrstivFinis via wp_localize_script(), and the scoring engine (maxWeights, score, careLane, results) runs entirely in the browser. The prototype's own privacy copy is the contract: client-side only — nothing stored or transmitted.

// includes/cpts.php — "Root-Cause Reflection Map" theme options (abridged) Container::make( 'theme_options', 'Root-Cause Reflection Map' ) ->add_fields( [ Field::make( 'complex', 'questions', 'Questions' ) ->add_fields( [ Field::make( 'text', 'tag', 'Tag' ), Field::make( 'select', 'ring', 'Ring' ), // mind | body | gut Field::make( 'textarea', 'q', 'Question text' ), Field::make( 'complex', 'opts', 'Answer options' ) ->add_fields( [ Field::make( 'text', 'l', 'Option label' ), Field::make( 'text', 'w_sleep', 'Weight — sleep' ), // 0–3 Field::make( 'text', 'w_mood', 'Weight — mood' ), // … w_hormones · w_gut · w_stress … Field::make( 'select', 'lane', 'Care-lane routing' ), ] ), ] ), ] );

Alternative rejected: a CPT for questions with answers as child posts. The reflection map is behavioral configuration, not editorial content. Clinicians update weights; daily content editors never touch it. A CPT would add an admin archive, a public rewrite slug, and REST exposure for data that must never leave the page — the opposite of the privacy posture. Theme options keep it in one screen, editable with clinical intent, and out of every public surface.

Approach Assessment
Theme Options container (chosen) One screen for the whole instrument; flattened weights are reviewable at a glance; localized to the client and scored in-browser — zero PHI transmission, nothing stored.
CPT with child answer posts Editorial machinery (archive, rewrite slugs, REST routes) for configuration data; public surfaces for clinical weights; a join model for what is fundamentally one screen.
Hardcoded in JavaScript Faithful to the prototype, but weight changes become developer tasks — and the practice loses the ability to tune its own instrument.
The privacy posture is architectural, not procedural. The intake form submits to an external endpoint and the site's own copy states that nothing written there is stored in the website's database. The reflection map extends the same posture: the weights live in theme options, the scoring runs client-side, and no answer ever touches a WordPress table. Where Dolphin's portal encrypts student data at rest, this build keeps patient-adjacent data out of the database entirely — the lighter compliance surface a marketing site for a practice can hold.

Summary

How this build diverges from Dolphin.

The pipeline is identical; the answers are not. The table below is the delta — every row is a place where the same pipeline question ("how should this prototype behavior become WordPress?") got a different answer because the domain demanded it.

Dimension Dolphin Academic Prep Integrative Mind-Body Psychiatry
Ambient theming Holiday capsules — 14+ date-based observances, discrete palettes Circadian phases — five hourly bands, continuous, dark-mode-stacked
Editorial body Structured CPT fields (services, coverage areas, FAQs) Native post_content + Carbon folio metadata (dek, pull quote, margin note)
Clinical config Portal settings, spoof mode in user meta Reflection weights in theme options, scored client-side
Signature tool Booking engine with atomic database locks Root-Cause Reflection Map with weighted mind-body-gut scoring
Compliance surface FERPA-minded portal — AES-256 at rest, audit trails HIPAA-aware marketing site — no PHI in the database at all
CPTs registered 9 4 (essay, series, service, resource)
Same pipeline, different answers. None of these decisions required pipeline customization. The circadian system was extracted as a shared utility exactly as the capsule system was; the essay model came from the same data-array classification rules; the reflection container came from the same configuration-vs-editorial test. The pipeline asks the questions — the prototype's own architecture supplies the answers.
