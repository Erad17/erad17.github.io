Portal Architecture

A dedicated WordPress plugin for secure family accounts — authentication, encrypted form submission, e-signatures with audit trails, document vault, and dual-notification system.

Plugin: dolphin-portal Encryption: AES-256 at rest Compliance: FERPA-minded
01

Why a dedicated plugin.

The portal is a custom codebase that owns the full data lifecycle — authentication, encrypted form submission, e-signatures with audit trails, document vault, and dual-notification system. It registers four custom post types behind custom REST endpoints, with role-based access for families, coaches, and administrators. Submissions are encrypted with AES-256 at rest, and uploaded files live outside the web root.

Approach Assessment Verdict
Custom plugin (chosen) Full architectural control, and no per-user licensing costs or vendor lock-in. Encryption that can be audited rather than trusted as a black box. Every data flow is documented and every permission check is explicit. The plugin ships as a single PHP file — zero external dependencies beyond Carbon Fields and Timber, both already in the theme stack. Chosen
Gravity Forms / Formidable Powerful form builders with mature ecosystems. However, student data flows through a third-party plugin with its own storage model, encryption guarantees, and update cycle. The licensing model charges per site — a recurring cost for what is effectively a data entry surface. Forms alone do not provide authentication, dashboards, or role-based access. Rejected
MemberPress / Restrict Content Pro Membership plugins handle authentication and role-based access but are not designed for custom portal workflows. Student data, encrypted submissions, and e-signatures would require extensive customization on top of a membership framework. The plugin becomes a dependency that constrains the data model rather than serving it. Rejected

2 · Access Control

Three roles, three dashboards.

Each role has its own dashboard view rendered server-side via Timber. The portal plugin registers three WordPress roles with granular capabilities mapped to custom post types. The portal.twig template handles both unauthenticated (login form) and authenticated (role-based dashboard) states. Because the portal shares its design tokens, rendering stack, and Carbon Fields data layer with the marketing site, it runs on the same WordPress install rather than as a separate app.

Role Inherits From Read Write Spoof
dolphin_family subscriber Own sessions, own forms, own documents, own notifications Book sessions, reschedule own sessions, upload documents, sign forms —
dolphin_coach editor Assigned sessions, assigned students Session notes (own sessions only), availability settings —
dolphin_admin administrator Everything Everything Yes — read-only, view-as any user, zero write capability
Spoof mode: read-only enforced at the REST API layer. When an admin activates spoof mode, a flag is stored in WordPress user meta. Every REST endpoint checks this flag before executing write operations. The admin sees exactly what the target user sees — their sessions, their forms, their documents — and nothing more, and because all POST, PUT, and DELETE requests return 403 while spoofing, there is no PHI exposure, no accidental writes, and no audit trail contamination.

3 · Data Architecture

Four CPTs, one authentication system, one student model.

The portal registers four custom post types — dolphin_session, dolphin_form_entry, dolphin_document, and dolphin_notification — plus a fifth (dolphin_student) added in Step 2a to link every session, form, document, and notification to a specific student. All post types use public => false, show_ui => true, and show_in_rest => true. Carbon Fields containers define every meta field. Storage is _-prefixed — the same convention used by the seed data — so Carbon Fields' meta_query rewriting applies to all dashboard queries.

CPT Key Fields Linked To
dolphin_session student_id, coach_id, service_id, session_date, duration, mode, location, status, notes, family_notes Student, Coach, Service
dolphin_form_entry student_id, form_type, status, signature_data, signature_date, countersignature_data, countersignature_date, form_data (JSON) Student
dolphin_document student_id, file (attachment ID), session_id, form_id Student, Session, Form
dolphin_notification type, message, icon, is_read, related_session_id, related_form_id, sender_id, reply_to Session, Form

4 · Encryption & Compliance

Designed to FERPA principles, even though FERPA doesn't apply.

FERPA (Family Educational Rights and Privacy Act) applies to educational institutions that receive federal funding — public schools, not private tutoring companies. However, the portal is designed to FERPA principles because the families using it have the same expectations:

  • Data minimization. Forms collect only what's needed for educational services. No marketing fields appear on intake or enrollment forms.
  • Access controls. Role-based. A coach sees only their assigned families, and a family sees only their own data. Admin spoof mode is read-only.
  • Encryption at rest. All form submissions are stored with AES-256 encryption. Files are stored outside the web root, referenced by UUID rather than filename.
  • Audit trails. Every signature, file upload, and form submission is recorded with timestamp and user. WordPress post revisions provide immutable history.
  • Data portability. Families can request their data as a structured export. Admins can export any record. No proprietary format lock-in.
  • Breach response. If the encryption key is compromised, it can be rotated via a WP-CLI command. Old submissions are re-encrypted without data loss.

5 · Booking Engine

Two families, one slot, zero double-books.

A family selects a student, a program, a coach, and a time. The system checks coach availability, enforces buffers between sessions, filters programs by student grade, and prevents double-booking with an atomic database lock. Confirmed sessions generate an .ics calendar file with Google Calendar and Outlook links.

Concurrency

Two families click "Book" at the same time for the same coach at the same slot. Two requests arrive simultaneously at POST /dolphin/v1/booking. The system must let exactly one through and reject the other with a clear message.

First approach: WordPress transients. set_transient('dolphin_booking_lock_{coach_id}_{slot}', time() + 10, 10). Set a transient, check it on the next request. The problem: WordPress's per-request object cache. A get_option() miss gets cached in memory. The second concurrent request thinks the lock doesn't exist — the transient was set but the object cache hasn't been invalidated. Both requests succeed, and the slot is double-booked.

The fix: Raw SQL INSERT IGNORE. Bypass WordPress's caching layer entirely. Write directly to the wp_options table with an atomic INSERT IGNORE, so the object cache never gets a chance to lie about whether a lock exists. The lock holder inserts a row with a 10-second expiry; the loser's insert is silently ignored, and a subsequent read confirms the lock exists. The loser gets HTTP 409 with "That time was just taken. Please pick another."

// Plugin: dolphin-portal — Booking REST endpoint // Atomic lock acquisition — bypasses WP object cache entirely global $wpdb; $slot_key = $date . 'T' . $start_dt->format('Hi'); $lock_key = 'dolphin_booking_lock_' . $coach_id . '_' . $slot_key; $now = time(); $inserted = $wpdb->query($wpdb->prepare( "INSERT IGNORE INTO {$wpdb->options} (option_name, option_value, autoload) VALUES (%s, %s, 'no')", $lock_key, (string) ($now + 10) )); if (1 !== $inserted) { $existing = $wpdb->get_var($wpdb->prepare( "SELECT option_value FROM {$wpdb->options} WHERE option_name = %s", $lock_key )); if (is_numeric($existing) && (int) $existing > $now) { return new WP_Error( 'dolphin_booking_locked', 'That time was just taken. Please pick another.', ['status' => 409] ); } // Stale lock — take it over $wpdb->update($wpdb->options, ['option_value' => (string) ($now + 10)], ['option_name' => $lock_key] ); }
Verified with parallel curl, not browser sessions. Browser keep-alive sockets serialize concurrent requests, so they would never trigger the race condition. The E2E test uses curl & curl & wait to fire two POSTs from separate TCP sockets: one consistently returns 200 with a session ID and .ics URL, while the other consistently returns 409 with "That time was just taken." 32/32 Playwright E2E tests passing, including concurrent booking, availability validation, spoof enforcement, and intake wizard full flow.

6 · Slot Generation

15-minute increments, buffer-enforced, UTC-safe.

The GET /dolphin/v1/availability-slots endpoint walks from the coach's availability block start time in 15-minute increments. A candidate slot qualifies only if it satisfies six conditions — the full session duration fits inside the block, the slot start is at least min_lead_time_minutes from now, no overlapping existing sessions with status confirmed/pending/rescheduled exist, the applicable buffer (travel for in-person, standard for video) applies on both sides, the date is not a blocked date, and the date is within the booking horizon. All comparisons in UTC. Returns start/end as HH:MM in site timezone plus ISO-8601 UTC. Capped at 40 slots. Compute-heavy work done server-side so the client never does timezone math.

7 · Form Engine

Form definitions as PHP classes. Submissions encrypted at rest.

Each form (student intake, SAT accommodations, enrollment, etc.) is a PHP class extending a Portal_Form base. The base class handles rendering, validation, submission storage, and notification dispatch. Individual forms define their fields and validation rules:

// Plugin: dolphin-portal/src/Forms/IntakeForm.php class IntakeForm extends Portal_Form { protected $form_type = 'intake'; protected $requires_signature = true; public function fields() { return [ 'student_name' => ['type' => 'text', 'required' => true], 'student_email' => ['type' => 'email', 'required' => true], 'student_phone' => ['type' => 'tel', 'required' => true], 'concern' => ['type' => 'select', 'required' => true, 'options' => CONCERNS], 'programs' => ['type' => 'multi_checkbox', 'options_callback' => 'get_programs'], ]; } protected function handle_submission($data) { $data['signature_data'] = $this->encrypt( $data['signature_data'] ); $post_id = wp_insert_post([ 'post_type' => 'dolphin_form_entry', 'post_title' => 'Intake — ' . $data['student_name'], 'post_status' => 'publish', ]); // Carbon Fields stores _-prefixed meta — same convention as seed data carbon_set_post_meta($post_id, 'form_type', 'intake'); carbon_set_post_meta($post_id, 'status', 'submitted'); carbon_set_post_meta($post_id, 'form_data', json_encode($data)); $this->dispatch_notifications($post_id, $data); return $post_id; } }

8 · Integration

Same install, same stack as the marketing site.

The portal lives on the same WordPress install as the marketing site, sharing its design tokens, its Timber/Twig rendering, and its Carbon Fields data layer. The portal plugin is a single file — dolphin-portal.php — required from functions.php, so there is no separate server, no microservice, and no authentication bridge to maintain.

The portal.twig page template handles both states: unauthenticated (login form rendered via the existing portal-login Twig component) and authenticated (role-based dashboard with sidebar navigation, student switcher, and widget grid). The intake wizard reuses the same overlay component pattern as the holiday capsule gallery, and the booking modal reuses the same focus-trap pattern. The reuse is deliberate — the same patterns carry through every surface, which keeps the architecture consistent rather than just the visuals.

Portal widgets (sessions, forms, documents, notifications) are server-rendered Twig partials that query CPTs filtered by the current user. The page template passes data to components via {% include "components/portal/..." with { variable: value } %}. Components never query data directly — they receive everything from the parent context. This is the same pattern used across the entire theme, from the marketing site to the portal dashboard to the analytics console.

9 · Testing

32/32 E2E tests. Concurrent booking verified at the database level.

The portal's Playwright E2E suite covers the full user lifecycle across all three roles:

  • Family workflow: login → dashboard → student switcher → booking modal (5 steps, grade filtering, coach cards, date strip) → confirmation with .ics download → intake wizard (4 steps, validation, typed and drawn signatures) → dashboard refresh → sign form → upload document → dismiss notification.
  • Coach workflow: login → today's sessions → session notes (rich text, HTML sanitization) → availability editor (Mon–Sun grid, blocked dates, save validation) → 7-day preview with capacity line.
  • Admin workflow: login → stats dashboard → session filters (client-side, no page reload) → form filters → spoof as family (read-only enforcement, 403 on writes, wizard opens but submit disabled) → spoof as coach → exit spoof.
  • Concurrent booking: parallel curl — one 200, one 409. The transient lock approach failed because the object cache poisoned the miss; the INSERT IGNORE approach succeeded because it is atomic at the database level. The transient failure took an afternoon to diagnose, which is about what you'd expect for a bug that only appears when two requests land within the same cache window.
Every test assertion maps to a business rule. A family cannot book SAT Prep for a 7th grader, a coach cannot write notes on an unassigned session, and an admin in spoof mode cannot submit an intake form. Availability save rejects overlapping blocks with field-level errors. These are not unit tests — they are business rules verified end-to-end through the actual WordPress REST API at real localhost ports.
