Architecture Decision Record

Dolphin Academic Prep
Rebuild Architecture

Each decision documents a structural choice — theme framework, content modeling, plugin philosophy, data architecture — with alternatives considered, rationale, and tradeoffs.

Project: dolphinacademicprep.com Current stack: Twenty Ten + Elementor Target stack: Timber v2 + Carbon Fields

Context

The site as it stands today.

The current dolphinacademicprep.com runs on a Twenty Ten theme — WordPress's default from 2010 — with Elementor + Essential Addons layered on top for page building. It uses Yoast SEO v28.4 for metadata and sitemaps, MonsterInsights v11.2.0 for Google Analytics integration, Ultimate FAQ for frequently asked questions, and WP Fastest Cache for performance, serving all CSS and JS through minified bundles. The Bluehost/Newfold hosting platform injects nfd-wb-animated-in MutationObserver code and a speculation rules prefetch script on every page — host-level behavior the client did not request and cannot control.

The rebuild replaces this accumulation with deliberate, documented architecture. The guiding principle throughout: every plugin that can be replaced by a purpose-built module will be. Every feature that can be expressed as version-controlled code rather than a third-party dependency will be. The client should own their site — not maintain a collection of someone else's decisions.

Why this matters The current site has at least 10 active plugins, each representing an update cycle, a compatibility surface, and a decision the current owner inherits without understanding. The rebuild targets approximately 4–5 purpose-built modules, so the client ends up owning the code instead of renting ten plugins.

Decision 1

Theme Framework

01

Timber v2 + Twig — custom theme, no page builder

Context. The current site uses Twenty Ten as its base theme with Elementor + Essential Addons for page layout. There is no child theme. The markup uses pre-HTML5 conventions (#wrapper, #header, #access) that predate responsive design patterns. Every WordPress core update risks overwriting customizations and reinserting "Proudly powered by WordPress" in the footer.

Option Assessment Verdict
Retain Elementor + add child theme Preserves the page builder dependency. The child theme fixes update breakage but leaves the 2010 markup underneath. The client still does not own their layout — Elementor does. Rejected
Kadence / GeneratePress + Gutenberg blocks Modern, performant, well-supported themes. Still a third-party dependency with its own update cycle. The block editor introduces editorial complexity for structured tutoring data — services, locations, FAQs — that do not benefit from freeform page building. Rejected
Full Site Editing (FSE) WordPress-native with no third-party theme dependency. However, FSE puts layout control in the block editor — the wrong abstraction for structured service data. The client needs to edit content (descriptions, pricing, coverage areas), not layout. Rejected
Timber v2 + Twig PHP handles data and logic. Twig handles presentation. Templates are readable by any developer inheriting the codebase — open views/single-service.twig and read the template structure directly. The client owns every file in their hosting account, with no page builder lock-in. Chosen

Rationale. Timber enforces separation of concerns — PHP controllers prepare data, Twig templates render it. No global WordPress functions called inside templates, and no digging the real content out of five filters and serialized page builder metadata to see what the_content() actually renders. When another developer inherits this site in three years, they read the template files directly and understand the data shape from the controller code.

Tradeoff. No drag-and-drop page building. The client edits structured fields in a custom admin panel, not visual blocks on a canvas. For a tutoring business whose content is services, coverage areas, and FAQs — not marketing landing pages — we accepted that trade. If a future page needs flexible layout, a custom Gutenberg block backed by Carbon Fields adds that capability without surrendering the entire site to a page builder.

Decision 2

Content Modeling

02

Custom Post Types + Carbon Fields — structured data over WYSIWYG pages

Context. The current site stores all content in standard WordPress pages and posts. Service descriptions are paragraphs in a WYSIWYG editor. FAQs are managed through the Ultimate FAQ plugin. Contact information is inline text in page content with hardcoded phone numbers. None of this content has schema.org markup. None of it is queryable across the site.

Option Assessment Verdict
Advanced Custom Fields (ACF) Industry standard, GUI-based field management. Fields sync via JSON files — a deployment step that can drift. The GUI is convenient but field definitions live partially in a database that must be kept in sync with version-controlled JSON. Rejected
WordPress block editor + block patterns No additional plugin required. But blocks are layout components, not data structures. A "service" is not a collection of blocks — it is a data entity with structured properties (name, description, grade range, pricing). The block editor cannot generate schema.org markup from block content. Rejected
Carbon Fields Fields defined as PHP code in version control, so there is no JSON sync step and no GUI drift. Every field group is a readable PHP file. Schema.org markup is generated directly from field data — no duplication. If the site adds a new content type, it is a PHP file in a plugin, reviewable in a pull request. Chosen

Rationale. Carbon Fields treats content structure as code — field definitions live in version-controlled PHP files, not a database that must be synced. A Service CPT with fields for description, grade_range, and pricing tier generates structured, queryable data. A Coverage Area taxonomy term carries county, zip range, and tutor availability fields. Schema.org markup — LocalBusiness, FAQ, BreadcrumbList — is rendered from the same field data, so nothing drifts because there is only one source.

Planned content types:

  • Service — name, description, grade_range, subject_category, pricing_tier
  • Coverage Area (taxonomy) — counties, zip_codes, tutor_availability
  • Team Member — name, bio, specialties, credentials, photo
  • Resource — title, external_url, grade_level, topic_category
  • FAQ — question, answer, category — replacing Ultimate FAQ

Tradeoff. Adding a new field requires a developer — or, more precisely, a commit. For a site with stable content types (services do not change shape monthly), this is acceptable. The alternative (ACF's GUI) trades version-control integrity for point-and-click convenience. This project prioritizes integrity.

Decision 3

Plugin Philosophy

03

Custom OOP modules over third-party plugins wherever feasible

Context. The current site runs at least six plugins that can be replaced by purpose-built code: Yoast SEO for metadata and sitemaps, MonsterInsights for Google Analytics, Ultimate FAQ for FAQs, VFB Pro for contact forms, Elementor + Essential Addons for page building, and Black Studio TinyMCE for sidebar widgets. Each is a dependency: an update can break the site, a vulnerability can compromise it, and the client has no visibility into any of them.

Current Plugin Replacement How
Yoast SEO v28.4 Custom OOP module Meta titles/descriptions from Carbon Fields data. XML sitemap via template + WordPress rewrite rules. Schema.org generated from CPT structure. Open Graph tags from post meta. Canonical URL management. The one Yoast feature not replicated — content analysis traffic-light — is replaced by a custom Vue component using open-source readability libraries.
MonsterInsights v11.2.0 Custom OOP module GA4 script injection via wp_head hook — a single action callback. A custom REST endpoint proxies the GA4 Data API for dashboard metrics, cached in a WordPress transient. No account connection wizard, upsells, or telemetry.
Ultimate FAQ FAQ CPT + Carbon Fields FAQ as a custom post type with question/answer fields. Schema.org FAQ markup generated automatically. Grouped by taxonomy. The existing FAQ content — including the detailed response on subject coverage from Pre-K to Adult — migrates into structured fields.
Elementor + Essential Addons Timber v2 + Twig theme Covered in Decision 1. All page layout moves to version-controlled Twig templates. No page builder dependency.
VFB Pro (forms) Custom form handler Contact form with validation, honeypot spam prevention, and encrypted storage. Email notification via wp_mail. Submission logging to a custom database table for audit trail.
Black Studio TinyMCE Carbon Fields widget areas Sidebar content managed through Carbon Fields theme options. No widget plugin required.

Rationale. MonsterInsights wraps Google's gtag snippet in a plugin with account setup wizards, dashboard widgets, and upgrade prompts. The actual functional requirement — "put the GA4 measurement code on every page" — is a single wp_head action. Similarly, Yoast generates meta tags, Open Graph metadata, and XML sitemaps — all from post data that Carbon Fields already owns. Generating a sitemap from CPT data is a template. Generating schema.org from field data is a function. Neither requires a plugin.

What stays as plugins. WP Fastest Cache (performance is infrastructure — its replacement is server-level Nginx FastCGI cache). A security plugin (Wordfence or equivalent). A backup solution with verified restores.

Tradeoff. The client loses Yoast's content analysis traffic-light and MonsterInsights' dashboard widget. In return, they gain a site with six fewer plugins to update, no plugin licenses to track, and full ownership of their SEO and analytics infrastructure. Both analysis and dashboard features are rebuilt inside the Vue admin panel — using open-source readability libraries for content scoring and the GA4 Data API for metrics — in a single interface rather than scattered across plugin metaboxes.

Decision 4

Coverage Area Architecture

04

Taxonomy-driven coverage areas with schema.org LocalBusiness

Context. The business provides in-home tutoring serving North/Central New Jersey and NYC. The current site has no location-based landing pages, no structured geo-data, and no way to associate services with coverage areas. A parent searching "tutoring in Montclair NJ" has no path to this site through local SEO.

Option Assessment Verdict
Individual pages per city Creates a maintenance burden: every new city requires a new page. Content duplication across pages. No canonical URL structure. The pattern that produces cloned pages with manual edits. Rejected
Google Business Profile only No on-site geo-signals beyond the GBP listing. Does not help internal site search or service-to-area associations. Rejected
coverage_area taxonomy A single taxonomy and template. Each coverage area is a term with county, zip range, and description fields. The template renders schema.org LocalBusiness markup with areaServed. Services associate with areas. Scales to any number of regions without new pages. Chosen

Rationale. A taxonomy fits how the business actually thinks about geography — "this business serves these areas." It is queryable (show all services available in Montclair). It is maintainable (add a coverage area = add a taxonomy term). It generates canonical URLs automatically (/coverage/montclair-nj/). Each term page carries schema.org LocalBusiness markup, which is the signal Google reads for "tutoring in [city]" queries.

Coverage areas planned: North Jersey, Central Jersey, NYC (Manhattan), Brooklyn/Queens, Staten Island, Westchester/Rockland County. Each term stores counties served, zip code ranges, and tutor availability notes — all editable through the Vue admin panel.

Decision 5

Family Portal

05

Dedicated WordPress plugin — auth, encryption, e-sign, notifications

Context. The project brief specifies a secure portal with login, approximately six fillable and signable forms, document upload with dual notifications, and sensitive student data handling. The current site has none of this — forms transmit data through VFB Pro without encryption at rest.

Architecture. A dedicated dolphin-portal plugin handles:

  • Authentication — WordPress user accounts with custom roles (family, coach, admin). Portal access restricted to authenticated users with appropriate capabilities.
  • Form engine — Form definitions as PHP classes. Each form renders as a multi-step wizard with progress persistence. Submissions stored in custom database tables with AES-256 encryption at rest.
  • E-signature — Canvas-based signature capture with audit trail (timestamp, IP, user agent). Rendered signatures stored as PNG, metadata as JSON.
  • Document vault — File uploads stored outside the web root with access controlled via PHP. Original filenames mapped to UUIDs. Download logging.
  • Dual notifications — wp_mail fired on submission to both family and admin. Templates overridable.

Rationale. Sensitive student data should not pass through a third-party form plugin, a SaaS form service, or an email attachment workflow. The portal plugin owns the entire data lifecycle: submission → encrypted storage → access-controlled retrieval → notification. It is a single plugin that can be audited, updated, or deactivated independently, and because the custom database tables persist, no data is lost if the plugin is ever removed.

FERPA-minded design. While FERPA applies to educational institutions receiving federal funding, the portal is designed to FERPA principles: data minimization, access controls, encryption at rest, audit trails for access and modification. This is a trust signal for parents who rightfully care where their child's educational data lives.

Decision 6

Editorial Interface

06

Vue 3 + PrimeVue admin panel — purpose-built, deactivatable

Context. The standard WordPress admin is a one-size-fits-all interface. For a tutoring business managing services, coverage areas, portal form submissions, and analytics — across staff with varying technical comfort — the default metabox-and-sidebar experience creates friction. A staff member updating a service description should not need to navigate to "Custom Post Types → Services → Edit."

Architecture. A dolphin-admin plugin loads a Vue 3 SPA (built with Vite, using PrimeVue components) on a custom admin page. The SPA reads and writes via the WordPress REST API, backed by Carbon Fields. The plugin enqueues its built assets only on its own admin page — zero performance impact on the rest of wp-admin.

  • Dashboard — service count, recent form submissions, analytics overview via GA4 Data API (cached)
  • Service editor — PrimeVue DataTable with inline editing via Dialog component
  • Form review — encrypted submissions decrypted for viewing by authorized users
  • Content quality — readability scores and SEO heuristics using open-source libraries, rendered inline in the editor

Fallback. If the plugin is deactivated, all content remains editable through Carbon Fields' native metaboxes. The admin panel is a UI layer — it does not own the data. The interface is a convenience over the data model, not the data model itself.

Rationale. The Vue admin panel provides an interface designed for this client's specific workflows rather than the generic WordPress admin, which handles every use case passably and none of them well. A staff member sees "Services" with an edit button, not a list of post types. The dashboard surfaces metrics this business actually needs: recent form submissions and service counts at a glance.

Decision 7

Holiday Capsule System

07

CSS custom properties + client-side calendar — zero server dependencies

Context. The project brief requests holiday-themed page looks for 14+ observances — Election Day, Diwali, Thanksgiving, Winter Holidays, Lunar New Year, and more — with banners, logos, and aesthetic changes scheduled a year in advance. The current site has none of this.

Architecture. The holiday capsule system uses CSS custom properties (--cap-a, --cap-b, --cap-glow) to theme the site, switched by a client-side JavaScript calendar that auto-detects the current date against a holiday schedule. Motif animations (falling leaves, floating diyas, drifting snow, swaying lanterns) are pure CSS with reduced-motion support. A gallery strip lets staff preview any capsule. A dropdown provides manual override of the automatic schedule.

Why not a plugin or server-side cron? A plugin that schedules theme changes via WordPress cron adds a database dependency for what is fundamentally a calendar lookup. The holiday schedule is static data — a JSON object — and the theming is pure CSS. The entire system has no server-side dependencies, no database queries, and no impact on page load beyond the initial CSS custom property swap. If the system fails, the site renders with its default theme rather than throwing PHP errors or a white screen.

Tradeoff. Adding a new holiday requires editing a JSON object and adding CSS keyframes — a developer task performed once per year. The alternative — a plugin with a holiday management UI — adds complexity for a task performed annually, and the simpler system is easier to keep working.

Decision 8

Hosting & Deployment

08

SiteGround or WP Engine — managed WordPress hosting, client-owned account

Context. The current site runs on Bluehost/Newfold managed hosting, evidenced by the nfd-wb-animated-in MutationObserver injection on every page and the nfd-wonder-blocks-utilities stylesheet. A speculation rules prefetch script is also automatically injected. These are host-level optimizations the client did not request and cannot control.

Recommendation. SiteGround or WP Engine, with the hosting account in the client's name and billing:

  • Client ownership. The hosting account, domain registration, and all credentials are the client's property. No developer holds the keys.
  • SSL. Let's Encrypt via the host — automatic renewal, no configuration required.
  • Backups. Host-managed daily backups with verified restore testing. No reliance on plugin-based backup solutions.
  • Performance. Server-level caching (Nginx FastCGI cache or equivalent). WP Fastest Cache may remain as a secondary layer but is no longer the sole performance mechanism.
  • Staging. One-click staging environments for testing updates before production deployment.

Deployment. Git-based workflow. Theme, plugins, and Carbon Fields configuration are version-controlled. Deployments use Git push to the host's Git integration or via SSH — nothing gets edited on the live server. The database is excluded from version control; content migrations use WP-CLI.
