§ The System

FIG 01 — THREE LAYERS, NO SERVER REV A — DRAWN BY Marho Eradiri

The problem. The project brief requests "holiday page looks" — themed banners and logos that change for Election Day, Diwali, Thanksgiving, Winter Holidays, Lunar New Year, and nine other observances, scheduled a year in advance. The obvious approaches — a WordPress plugin, a server-side cron job, or a manual process where staff update the homepage before every holiday — all fail in different ways: plugins add database dependencies for a calendar lookup, cron jobs require server access the client shouldn't need, and manual updates will be forgotten by March.

The answer. Three layers, none of which require a server:

1
A static holiday calendar

A JSON object maps 14 holiday definitions to date ranges. Each definition specifies a display name, greeting message, date window, a two-color gradient palette, and a motif type. The calendar is a single data structure — editable in any text editor.

2
A client-side date checker

On page load, a JavaScript function compares the current date against the calendar. If the date falls within a holiday window, that holiday's palette is applied. If no holiday is active, the default "Open Enrollment" capsule is used. The check runs once, takes microseconds, and produces no network requests.

3
CSS custom properties for theming

Three CSS variables — --cap-a, --cap-b, and --cap-glow — control every themed element on the page. The hero gradient, the capsule ribbon, the motif animations, the greeting text, and the accent colors all derive from these three values. Changing a holiday means changing three hex codes in the calendar JSON.

Why Zero Server Dependencies Matters

A WordPress plugin that schedules theme changes via cron adds a database table, a settings page, and an update surface — for what is fundamentally a calendar lookup. The holiday schedule is static data. The theming is pure CSS. The entire system has no database queries, no PHP execution, and no impact on page load beyond the initial CSS variable swap. If the system fails, the site renders with its default theme — no PHP errors, no white screen, no broken layout.

§ The Motif System

Pure CSS animation. No JavaScript animation loop. No canvas. Each capsule has a motif property that determines which CSS-only animation plays in the hero section background — decorative particles rendered as styled <span> elements with keyframe animations:

Motif Visual Animation CSS Technique
leaf 13×13px teardrop, gradient fill Fall + rotate over 7–15s @keyframes fall — translateY + rotate
snow 7×7px white circle with blur shadow Gentle drift over 8–12s @keyframes fall — translateY, slower duration
diya 10×10px radial gradient with glow Float upward over 9–14s @keyframes rise — translateY(-660px)
petal 10×14px asymmetrical border-radius Fall + slight horizontal drift @keyframes fall — translateY + rotate
star 12×12px clip-path polygon, static position Twinkle in place @keyframes twinkle — scale + opacity pulse
lantern 11×15px rounded rectangle with glow Gentle sway at anchor point @keyframes sway — rotate ±9° with transform-origin: top
spark 5×5px circle with colored shadow Subtle twinkle, widely scattered @keyframes twinkle — lower opacity range

Each motif spawns 14–16 particles positioned randomly across the hero area. Every particle gets a randomized duration (7–15 seconds) and delay (0–9 seconds) so they never move in lockstep. The result looks organic — not like a screensaver from 1998. The entire animation system is approximately 120 lines of CSS.

Reduced Motion Support

Every animation respects the user's prefers-reduced-motion: reduce media query. When enabled, all motifs are hidden entirely — no falling leaves, no drifting snow, no animated particles of any kind. The color palette and greeting message change, but nothing moves. This is not optional — it's an accessibility requirement, and it's implemented in a single CSS rule.

§ Staff Controls

Preview any capsule. Override the calendar. No training required.

1
Gallery strip preview

A row of capsule cards on the homepage lets staff click any holiday to preview it live. The preview applies the capsule's colors, greeting, and motifs immediately — but only for the current session. Refreshing the page returns to the calendar's automatic selection. The "Automatic" card is selected by default.

2
Dropdown override in the header ribbon

A small dropdown in the capsule ribbon (top of every page) lets staff manually select a capsule. Selecting "Auto" returns to calendar-driven behavior. Selecting a specific holiday overrides the calendar for the current session — useful for testing or for extending a holiday theme a few days beyond its window.

Both controls are client-side only. They do not persist to the database. They do not affect other visitors. They are preview tools, not content management — the calendar is the source of truth, and staff can look ahead to verify what will display on any given date. These interactions happen on the front end of the site — no wp-admin login required. The people who care about the holiday theming are not necessarily the people who are comfortable in the WordPress admin.

§ What This Replaces

Approach Assessment Verdict
WordPress plugin (holiday/seasonal theming) Adds a plugin to the update queue for a feature that is fundamentally a calendar lookup. Most holiday plugins are designed for e-commerce sale banners, not subtle brand theming. Adds database tables, settings pages, and compatibility surface. Rejected
WordPress cron + theme options Server-side scheduling with a theme options panel for holiday configuration. More control, but requires WordPress cron to be reliable (it isn't, without a real cron job). Staff must log into wp-admin to manage holidays. Couples the feature to the server. Rejected
Manual updates (staff edits page before each holiday) Zero technical complexity. Also zero chance of consistency — holidays will be forgotten, colors will drift, and the January intern won't know how to configure the Diwali banner. Rejected

§ Failure Modes

Scenario Behavior Impact
JavaScript fails to load (blocked, errored, or disabled) The calendar check never runs. CSS variables remain at their default values. The site renders with the default "Open Enrollment" theme. Zero — the site is fully functional and on-brand.
A holiday definition has a malformed date range The date comparison function skips that capsule and falls through to the default. Zero — the site degrades to default, not to broken.
Two holidays overlap (date range conflict) The first matching capsule in the array wins. The calendar is ordered by priority — more specific holidays precede broader ones. Minor — the wrong holiday displays, but the site remains functional.
CSS custom properties are not supported (very old browsers) The var() calls resolve to nothing. Themed elements render with their fallback inline styles. The site layout is unaffected. Zero — the tutoring demographic does not use IE11.
Staff selects a preview capsule and forgets to switch back The preview is session-only. Refreshing the page or opening a new tab returns to calendar-driven theming. The dropdown always resets to "Auto" on page load. Zero — previews cannot persist accidentally.
Design Principle

The system should fail to default, never to broken. Every failure mode results in the site rendering with its standard brand colors. No PHP errors, no white screen, no "holiday plugin requires update" admin notice. The capsule system is a decorative enhancement — when it fails, the site is still a fully functional tutoring platform with its professional brand intact.
